# 从论文到实现：集中调度与老化资源准入

## 来源及边界

[AIOS 论文 v5，§3.3 与附录 A.3](https://arxiv.org/html/2403.16971v5#S3.SS3) 将 Agent 服务请求集中排队，比较 FIFO 与 RR。RR 依赖其上下文中断/恢复支持；本项目的远程供应商接口没有该能力。因此保留 FIFO 基线，借鉴集中请求管理，不将杀掉 Worker、重新请求或停止读取响应称为 LLM 推理抢占。

[Linux CFS 官方设计文档 §2](https://docs.kernel.org/scheduler/sched-design-CFS.html) 通过运行时间记账和选择落后实体维护公平性。本项目仅参考“不能一直让部分工作获得服务”的设计目标；没有复制 vruntime、红黑树、CPU 抢占或 EEVDF。

新增 `aging_fit` 是本项目组合机制：多维资源适配 + 有限等待后的排空预留，并非 AIOS 论文原有算法或新的学术发明。代码独立编写，未复制 AIOS 调度器实现。

## 算法

Runtime 维护实际资源预留；AdmissionScheduler 只选择下一项依赖已满足的 Task：

1. 记录首次进入 ready 集合的单调时间戳。依赖尚未满足的时间不算排队老化。
2. 未达到老化阈值时，选择当前 CPU、内存、pids 总预算能容纳的任务，允许绕过暂时放不下的大任务。
3. 存在等待超过阈值的任务时，选择最老者；同龄以首次到达顺序打破平局。
4. 最老任务暂时放不下时，停止填入后续小任务，让已运行 Attempt 自然完成、超时或取消并清理后释放资源。资源足够即启动该任务。
5. 超过总预算的请求由 Runtime 标记 unschedulable，不能触发排空；同 Agent 正在执行的任务也不触发全局排空。

排空不杀进程，不提前释放账本，不修改 cgroup 实际限制，也不要求供应商支持取消。

## 接口

```python
scheduler = AdmissionScheduler(policy, budget, defaults, aging_seconds=2.0)
decision = scheduler.choose(
    ready_tasks, used, busy_agents=busy_agents,
    slots_available=max_workers-len(running),
)
```

每次调用传入完整的、依赖成功且处于 waiting 的集合，包含暂时被同 Agent 串行约束挡住的任务。成功启动后更新 running/used，再传入剩余 ready 集合选下一项；任务离开 ready 集合即清除旧等待年龄。Decision 返回 task_id、reason、draining_task_id、waited_seconds，供调度与可视化显示。现有 fifo/resource_fit 可继续作为独立基线。

## 可验证效果与取舍

确定性测试构造“一半资源一直被占用，另一半不断填入短任务”的队列：纯 resource_fit 持续跳过需要全部资源的大任务；aging_fit 到达阈值后停止填充，旧运行任务释放资源后首先启动大任务。另测内存维度、同 Agent 串行、超总预算、FIFO 队首阻塞和年龄重置。

这证明该构造中的旁路次数受控，不证明任意负载下吞吐或尾延迟更好。排空会暂时降低利用率，阈值越短越接近严格排队，越长越偏向填充。等待上界还依赖所有已运行任务有有限期限、清理能够收敛以及新 ready 任务不会抢走已积累的年龄；没有对不释放资源的 Worker 作无条件无饥饿承诺。

测试运行：`python3 -m unittest -v test_scheduling`。真实多任务实验应记录每项 ready 时间、开始时间、完成时间、等待原因、资源利用率，并对比 fifo/resource_fit/aging_fit；不要将 AIOS 论文中的加速比直接用作本项目结果。
