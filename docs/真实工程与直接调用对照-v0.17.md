# v0.17真实工程与直接调用对照

2026-11-16，Asia/Shanghai。结论：减少付费路由与重复源码生成已经落地，但本次工程主实验尚未证明 Runtime 总体更快、更省或更准确。精简单 Agent 循环仍比 Runtime 轻。简单无状态回答的后续补充实验已消除额外提示包装，实际输入/输出 token 与使用相同系统提示的直接调用相同。

原始数据在 validation/engineering-2026-11-16/。本轮共83次真实模型请求：首次错误测量脚本28次、修正后的主实验45次、独立失败反馈试验1次、无状态补充8次、网页附件验收1次。全程未导出供应商Key，没有付费POST自动重放，所有失败与慢样本保留。

## 主实验与公平口径

主实验冻结版本 da120c0fb0737e743b6042113aabe2ff9f9ac019。12个工程案例，包含三个受控项目各2次，以及多文件配置解析、日志汇总各3次。另有4个简单问题。工程每例三组，简单问题每例两组，总共44个执行样本。固定种子、循环改变组顺序、同一 deepseek-flash broker、关闭原生深度思考、单次4096输出上限、新进程、新cgroup、同为2核/1GiB/128pids、Runtime最多2个Worker。

| 组 | 定义 |
|---|---|
| 直调加验证 | 一次模型生成，随后运行与Runtime相同的真实本地验证，不允许第二次修正 |
| 精简循环 | 相同专门状态机、初始数据、模型指令与验证，最多修正一次，不使用Runtime DAG/Worker |
| Runtime | 公共auto_tasks入口、实际Worker和cgroup、专门修复状态机，最多修正一次 |

这不是把裸HTTP生成时间与完整工程验证时间直接相除：三组端到端时间都包括准备与实际验证，外部独立评分都排除在测量外。模型请求耗时另外记录。直调仅一次、循环最多两次，允许的推理机会不同，实际次数全部计入。

评分器先检查错误原版失败、已知参考实现通过。新增工程的额外测试留在Agent工作目录之外，受控项目再使用85/120/120个额外用例。完成要求本地验证、独立测试、测试未改和交付源码哈希一致同时满足，状态succeeded不等于业务成功。此处“隐藏”仅指未交给本次模型请求，数据与评分器现随证据公开。

## 工程结果

| 指标，12例 | 直调加验证 | 精简循环 | Runtime |
|---|---:|---:|---:|
| 完成质量 | 10/12 | 12/12 | 11/12 |
| 端到端耗时中位数 | 1.972秒 | 2.223秒 | 2.548秒 |
| 实际模型请求 | 12 | 12 | 13 |
| 实际输入token合计 | 13,835 | 13,835 | 14,828 |
| 实际输出token合计 | 3,526 | 3,876 | 4,257 |
| 实际总token合计 | 17,361 | 17,711 | 19,085 |
| 本机CPU时间中位数 | 0.265秒 | 0.266秒 | 0.512秒 |
| cgroup内存峰值中位数 | 22.85MiB | 23.02MiB | 35.38MiB |

Runtime比直调的中位耗时高约29.2%，总token高约9.9%。11/12与10/12相差一个案例，不能归因于架构提高准确率；精简循环本次甚至没有用到第二次调用，其12/12与直调差异也包含模型采样波动。

相比历史多次路由流程，当前每例只用1—2次模型生成，避免了重复分析与最终源码重写。历史数据任务条件不同，因此不报告一个跨批次正式降幅。

## 主要瓶颈与失败

Runtime工程组的模型请求等待占总样本耗时约76.95%。同组的非模型部分中位0.691秒，直调/精简循环约0.30秒，主要包含进程、序列化、协调、准备和验证。当前收益应继续围绕减少调用与提示、改善失败反馈；不能仅把调度唤醒加快就当作端到端优势。

供应商缓存也不一致：工程组直调/精简循环各有9,856个缓存输入token，Runtime为2,560；未缓存输入分别3,979和12,268。相同事实的JSON序列化顺序不同，缓存及网络时延可能影响结果。没有固定采样参数、缓存控制或现金账单，不换算费用，也不作显著性结论。

Runtime失败于 pricing_1：模型把整行折扣向下取整写成先对折扣额取整，第二次提交相同错误源码。旧验证器只返回公共失败数量，缺少具体断言。随后补充公共失败输入、预期与断言，并复用完全相同的失败验证，隐藏用例答案未暴露。

修补后的独立反馈试验保留真实错误源，向一个真实模型提供公共失败信息；模型生成了受控AST子集不允许的三元表达式，验收仍失败，安全检查未放宽。此结果在 correction-feedback.json，不能宣称该问题已由真实模型完全解决。新增机制经过免费回归验证，但修补后没有重新完成整套工程A/B，主表仍是冻结版本结果。

## 简单问答补充实验

主实验4题中，旧轻量路径Runtime输入528、输出24token，4/4通过；裸直调输入92、输出14，2/4通过，失败是返回标量而非要求的JSON对象。这既有提示负担，也有格式指令差异。

后续版本 eb639a0abe931e67a4fa5a7a91d28034ac32147c 删除无状态请求的JSON上下文包装和无关资料说明。对同4题重新声明独立方案，直调与Runtime使用完全相同的简短系统提示和用户消息。逐对消息SHA一致：

| 指标 | 同提示直调 | 新无状态Runtime |
|---|---:|---:|
| 完成质量 | 4/4 | 4/4 |
| 请求次数 | 4 | 4 |
| 实际输入token合计 | 136 | 136 |
| 实际输出token合计 | 24 | 24 |
| 端到端耗时中位数 | 1.034秒 | 1.086秒 |

对同4题，Runtime输入从528降至136，减少74.2%；这是删除提示包装的收益。新Runtime仍比同提示直调慢约52毫秒，不能说更快；两批并非随机交错的版本对照，不把批次速度差异全部归因于代码优化。

## 测量错误、安全与复现

最初脚本把Runtime参数max_workers写成workers，Runtime组在模型调用前退出，仍消耗了另两组28次请求。invalid-harness.json完整保留，不能计作性能结果。补测前修正参数并加离线子进程执行检查，没有根据模型答案调整主实验产品提示。修正版独立冻结，保留相同数据SHA，未覆盖原记录。

主实验45次请求均有usage且finish_reason=stop。两次正式比较剩余样本cgroup均为0。Linux发现242项、234通过、8环境跳过，另19项严格检查通过；最后的无状态和解析小修改再运行26项相关检查。网页附件验收另以1次真实调用修复加法模块、通过3项测试，测试原文哈希不变，浏览器核对源码下载入口。

真实凭据只留在既有内存broker，PID1477始终保留。SQLite备份与生产会话没有进入公开证据。源码、方案、数据、失败、方法复算和网页验收均随功能分支交付。复现应使用新目录与新意图，不重放已有付费记录；查看各protocol中的提交与runner哈希，主实验与后续修补版本分开核对。
