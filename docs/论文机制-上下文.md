# 论文机制：Agent 上下文的有界 LRU-2 缓存

## 来源与范围

已阅读 [AIOS: LLM Agent Operating System，arXiv v5，第 3.5 节及附录 A.5](https://arxiv.org/html/2403.16971v5#S3.SS5)。论文将 Agent 历史、工具结果作为运行时内存管理对象，并讨论容量不足时用 LRU-K 在 RAM 与持久存储间管理这些对象。本地 references/aios.txt 是项目 README，不能代替论文原文。

本实现选取 LRU-K 的 K=2，适配本项目的不可变 JSON 对象存储。LRU、LRU-K、gzip、内容哈希均为已有技术。本项目将它们与工作流授权、消息引用和 cgroup 执行组合，作为可复现实验机制，不将这些算法声称为原创，也不宣称完全复现 AIOS 内存管理器。

没有实现供应商 GPU KV Cache 共享、LLM token 生成状态快照、文本有损摘要或 LLM 调用抢占。

## 具体实现

`ContextStore(root, cache_bytes=8*1024**2, cache_policy='lru2', cache_max_entries=1024)` 保持旧的 put/get/stats 接口，默认启用 8 MiB 原始 JSON 字节缓存。`cache_bytes=0` 禁用缓存，`cache_policy='lru'` 是单次最近访问基线。

磁盘仍保存 SHA256 命名的唯一对象，并按收益选择 gzip。读取未命中时，读取和解压对象、验证内容哈希，再将原始 JSON 字节加入缓存。每个对象记录最近两次驻留期内的访问序号。淘汰时先移除仅访问一次的对象；成熟对象之间比较倒数第二次访问。与保留全历史的 LRU-K 实现不同，这里对象淘汰后不保留访问历史，减少元数据量。因此这是有界、无幽灵历史的 LRU-2 变体。

缓存同时受原始 JSON 总字节数和条目数约束，超预算的大对象只读不缓存。字节预算不包含 Python 字典、序号、stat 元组等元数据，也不等价于进程 RSS 硬限额；条目数上限用于约束小对象元数据增长，实际进程内存仍由 cgroup 限制。

每次 get 均先校验授权，再检查磁盘对象的设备号、inode、大小、mtime_ns 和 ctime_ns。文件变化则使缓存失效，并重新读取校验。缓存命中时也对缓存字节校验内容哈希；每次 JSON 反序列化产生新对象，调用方不能通过改动返回值污染其他 Agent 的后续读取。磁盘文件及 gzip 解压后的对象均最多 1 MiB，文件读取也使用显式长度上限，避免 stat 之后文件变大时无界读取。

该完整性策略旨在检测普通文件替换/修改；它不是针对恶意 root、同 OS 身份恶意代码或并发文件系统对抗的安全沙箱。授权和缓存都仅在当前控制进程内生效，重启后不恢复授权索引。

## 指标与验证

原有 puts、unique_objects、logical_bytes、stored_bytes 定义保持不变。新增 cache_hits、cache_misses、cache_evictions、cache_invalidations、cache_bypasses、cache_bytes、cache_entries、cache_limit_bytes、cache_limit_entries、cache_policy、disk_reads、disk_read_bytes。

```bash
python3 -m unittest -v test_context_cache
python3 tools/benchmark_context.py --rounds 8 --repeats 3
```

测试覆盖缓存命中不越权、返回值可变隔离、字节/条目上限、大对象绕过、关闭缓存基线、热对象抵抗单次扫描和文件修改检测。基准比较禁用缓存、LRU、LRU-2 三种模式：两个共享热点与一次扫描对象交替出现，保存每次用时及读取计数到 reports/context-benchmark.json。每轮反转部分执行顺序，降低固定顺序偏差。

disk_reads 是本实现打开文件并调用 read 的次数，disk_read_bytes 是读取的压缩/未压缩文件字节数，不是物理盘 IO，内核页缓存仍然启用。时间包括 JSON 解码和 SHA256 校验，不能保证所有负载都更快，也不能直接外推到模型 token 成本或整个 Agent 工作流吞吐。
