| [Ray，OSDI 2018](https://arxiv.org/html/1712.05889)，§3.1—3.2、4.2.3 | 上下游结果使用不可变对象引用；调度描述与数据获取分开 | 共享内存零拷贝、分布式对象存储、lineage 自动重算 |
| [MemGPT v2](https://arxiv.org/html/2310.08560v2)，§2.1—2.4 | 区分对象缓存与模型上下文窗口；本轮保留无损对象压缩 | 已实现其模型自主分页、递归摘要或无限上下文 |

以上是来源明确的机制借鉴。Agent 父 cgroup、生命周期授权撤销与资源账本的组合是本项目实现选择，并不因为组合就成为已证实的学术原创。

## 实现关系

```text
AgentControlBlock（身份、模式、并发、预算）
       │ 当前各维资源预留
       ▼
AdmissionScheduler(drf) ──最低主导份额──► Attempt
       │                                │ 临时 capability
       │                                ▼
全局账本 / Agent 账本           Broker.get(ref) → 授权检查
       │                                │
Agent 父 cgroup                          ▼
       └── Attempt 子 cgroup      ContextStore（哈希 / 压缩 / LRU-2）
                                        ▲
                              成功结果发布，不可变引用
```

### 按 Agent 公平准入

`dominant_share(a) = max(reserved[a][r] / workflow_budget[r])`，维度为 CPU、内存、pids。计量的是预留额度，不是抖动的实际 CPU 使用率。相同 Agent 的在途任务先聚合再比较，不能靠拆成多个 Task 取得多个独立份额。

只在依赖就绪、Agent 未暂停/终止、有并发槽且满足 Agent 预算的任务中选择；份额相同按进入就绪集的次序决定。最低份额任务暂时放不下时停止回填，等在途 Attempt 释放预算。没有杀死、冻结或抢占运行中的任务；暂停或 Agent 预算受阻的任务不锁住其他 Agent 的准入。每次决策检查 Agent 预留之和等于全局账本，发现失配拒绝使用错误数据。

它属于单工作流、等权、不可抢占准入策略。当前没有跨工作流公平性、历史 CPU 服务量公平性或云模型 token 公平性。小任务也可能被大任务阻塞，默认策略仍为 `resource_fit`。网页增加 DRF 选项，资源页显示当前各 Agent 主导份额。

### 引用数据流

过去启动载荷会重复包含 `contexts`、解码后的 `_contexts` 和 `_inputs`。现在协调器将上下文及成功输出写入同一个不可变对象仓库，启动载荷只带 `_context_refs` / `_input_refs`。Worker 在使用前通过本机 Broker 读取；临时凭据绑定 Agent 身份，不能用自报身份越权。

结果引用只向声明 `inputs` 且满足直接依赖的消费者授权。协调器保留内部发布权限，生产者随后终止也不使已提交结果失效；终止消费者仍撤销其读取权限。摘要中的 `dataflow` 以及 `running` 事件中的 `input_refs` 可追溯投递。现有工程修复、评审路由和模型提示词仍收到相同的数据类型。

这减少的是启动载荷中的重复正文。Broker HTTP 传输、JSON 解码、Worker 物化、事件与结果文件仍有复制；API 授权也不能隔离有同一 Linux 用户任意文件/网络权限的恶意程序。单个对象仍限 1 MiB。

## 赛题 4.1—4.7 对照

| 要求 | 当前实现与证据位置 | 剩余限制 |
|---|---|---|
| 4.1 国产开源 OS | openEuler NUC；委派服务中的 Linux 验收 | 尚无第二发行版的同等完整验收 |
| 4.2 依赖、动态、资源调度 | DAG、原子动态批次、四策略；`test_paper_mechanisms.py` 复现 DRF 双用户示例 | 公平性与吞吐各有取舍；没有真实任务上的 DRF 优势证据 |
| 4.3 统一 Agent 抽象 | ACB、生命周期、双层 cgroup、Agent 管理网页 | Agent 生命周期限于工作流；未增加 Linux 内核原生 Agent 类型 |
| 4.4 容错 | Attempt 隔离、超时/OOM、受限重试、撤销、回收失败隔离 | 依赖失败会跳过相关分支；控制器崩溃后不自动续跑 |
| 4.5 上下文复用/压缩/隔离 | SHA-256、gzip、LRU-2、授权；本轮将依赖数据接入引用通路 | 无 KV Cache；HTTP/解码非零拷贝；磁盘产物无自动配额淘汰 |
| 4.6 复杂真实场景 | 三类 Python 项目修复，历史真实 API 重复实验 | 本轮采用离线可复现测试，不把旧实验当作新机制性能证据 |
| 4.7 通信 | 有界邮箱、消息 ID / ACK、临时凭据、引用读取 | 本机 HTTP；内存邮箱不持久，非恰好一次交付 |

## 验证与复现

常规检查：`python3 -m unittest -q`。专项：`python3 -m unittest -q test_paper_mechanisms`。严格测试需要可写的委派 attempts 子树，并设置 `AGENTRT_TEST_CGROUP`；不得把全部 Runtime 作为 root 运行。

在同一受限服务内运行：

```bash
python3 tools/benchmark_references.py \
  --baseline /home/tzd/agent-runtime-v07-20261114 \
  --candidate /home/tzd/agent-runtime-v08-20261114 \
  --output reports/reference-benchmark.json
```

对照工作负载为四个消费者共享上游结果和上下文，4/96/256 KiB 三种尺寸，各重复三次、交错先后顺序；全程真实 Worker、相同全局预算、相同并发、无模型调用。记录端到端时间与消费者启动 JSON 字节数；后者排除 Broker GET、结果和事件，不能作为总网络流量指标。初次实验发现 HTTPServer 默认关闭轮询造成约半秒固定成本，已经缩短 Broker 轮询并重新验收。最终原始数据与在线验收记录保存于 `validation/papers-2026-11-14/`。

使用：网页选择免费“文档处理”，输入文本，选择 DRF 后运行；在资源页查看份额与引用投递，在任务页核对结果。CLI 可用 `python3 -m agent_runtime --policy drf --tasks examples/agent_tasks.json --agents examples/agent_specs.json`。

## NUC 实测结果

完整常规检查 150 项：142 通过、8 按环境跳过；另在真实委派 cgroup 下运行 8 项严格检查，全部通过，包含内存 OOM、pids、脱离进程组的后代清理、超时重试、Agent 聚合限额和本次引用数据流。最后对账无残留 cgroup。最终一次 Agent 引用登记调整又补跑 23 项相关检查（22 通过、1 环境跳过）。

| 每份共享正文 | 旧版消费者启动载荷总量 | 引用版载荷总量 | 旧版总耗时中位数 | 引用版总耗时中位数 |
|---|---:|---:|---:|---:|
| 4 KiB | 50,024 B | 1,636 B | 0.2759 s | 0.2964 s |
| 96 KiB | 1,180,520 B | 1,636 B | 0.3109 s | 0.3100 s |
| 256 KiB | 3,146,600 B | 1,636 B | 0.3798 s | 0.3805 s |

每行来自三次重复；每次四个消费者都验证结果一致。启动载荷减少约 96.7%—99.95%，但小输入略慢，中大输入耗时接近。结论是控制载荷缩小和数据流授权统一；没有稳定端到端加速证据，也没有测量总内存复制量。DRF 使用论文构造验证分配正确性，未进行付费真实任务上的优劣比较。

在线网页实测“文档处理 + DRF”4/4 任务成功、0 模型调用，上下文引用投递 2 次、结果引用投递 2 次；资源页显示四个 Agent 的主导份额与归零预留。原有模型代理 PID 保持不变，密钥配置保留。
