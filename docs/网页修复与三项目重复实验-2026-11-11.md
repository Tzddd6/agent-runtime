# 网页修复与三项目重复实验（2026-11-11）

完整观测：已收集 54/54 次，成功 51 次、失败 3 次。数据只能支持受控修复流程已实际执行，不能据此宣称性能优势。

## 网页工程闭环

控制台提供三个 Python 修复项目。实际顺序为：原版失败 → 分析与测试建议（可并行）→ 生成补丁 → AST 检查与不可变公开/隐藏测试 → 独立评审 → 校验评审结论及源码 SHA256。测试不通过时停止后续评审；原版红、修复绿与最终接受分别展示。

三个项目分别覆盖整数金额与舍入、半开时间区间与时间桶/TTL、Unicode 空白及文本规范化。它们是固定小项目，不是任意仓库上传执行器。

## 等待、资源、token 与费用口径

已观测运行合计调用 213 次；token：`{"prompt_tokens": 137627, "completion_tokens": 46747, "total_tokens": 184374, "prompt_cache_hit_tokens": 49019, "prompt_cache_miss_tokens": 88608}`。费用按本次指定费率（每百万输入未命中 2 元、命中 0.04 元、输出 8 元）估算为 **0.553153 元**，所有输入均按未命中计为 0.649230 元。未与供应商账单核对，实际费用未知。

另列凭据迁移 handoff 验证：1 次调用、11 token、估算 0.000034 元，不计入 54 次实验。

另列 GUI 一键修复 smoke：4 次调用、3916 token、估算 0.010401 元。整轮（矩阵 + handoff + GUI）合计 218 次调用、188301 token、估算 0.563588 元。

以上采用高峰费率保守估算，并非实际账单。[DeepSeek 官方定价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)区分峰谷时段；本轮实验在 18:22 后运行，仍统一以高峰费率估计，没有把低谷折扣作为实际已支付金额。此处未做汇率折算，最终金额以服务商账单为准。

就绪等待按真实 Worker 事件计算：任务首次 running 时间减去依赖最晚完成时间；baseline 采用作业创建时间。动态 review 从 validate 完成开始计，gate 从 validate/review 都完成开始计。此值包括控制器与进程启动开销，不能称为纯资源排队时间。逐任务等待与每次运行的等待和均保存在 JSON。

每次运行的就绪等待总和：1.053 [0.069, 7.733] 秒。Worker CPU 时间：0.490 [0.308, 0.516] 秒，来自终态 cgroup cpu.stat 的 usage_usec 累加；不含控制器、模型代理或云端模型 CPU。

每次运行的最大内存采样值：10618880.000 [6090752.000, 17481728.000] 字节。它取 history 内各活动 Worker 的 memory.current 采样总和最大值，**不是实际同时峰值**；也不包含控制器、代理及云端内存。

## 失败与限制

失败分类：`{"patch_policy_rejected": 1, "immutable_tests_failed": 2}`。策略/AST 拒绝依据 validation.error 分类；安全但不正确的补丁依据公开/隐藏测试失败分类。原始错误文字与源码保留在受限原始证据，不进入此摘要。

每格仅 n=3，且模型服务负载、回复长度、供应商前缀缓存会影响耗时和费用；交错执行不能消除这些影响。这个 DAG 只有分析与测试建议两个并行分支，几乎没有资源竞争，不足以检验复杂调度场景的优势。只报告观测，不做显著性、因果或性能优势推断。
