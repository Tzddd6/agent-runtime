# Agent Runtime Benchmark 评测方案

> 状态：评测设计草案（待实施与验证）  
> 日期：2026-11-17  
> 目标仓库：`Tzddd6/agent-runtime`，建议路径：`docs/benchmark-evaluation-plan.md`

## 一、评测目标

评测不同 Agent Runtime 在相同任务、模型、工具和硬件下的系统表现，而不仅是 Agent 的智能水平。

核心问题：
1. 任务正确性：能否完成任务？
2. 性能：延迟、吞吐量和调度成本如何？
3. 效率：CPU、内存、token 与费用多少？
4. 扩展性：多 Agent 并发增加后表现如何？
5. 可靠性：能否隔离故障、正确恢复？
6. 机制有效性：调度、上下文和资源控制分别有什么收益？

对照框架：自研 Agent Runtime、LangGraph、AutoGen、CrewAI，以及可选的 Google ADK。

参考框架：
- [AgentRace](https://agent-race.github.io/home)：时间、token、通信量、任务质量的跨框架效率比较。
- [τ²-Bench](https://github.com/sierra-research/tau2-bench)：真实工具交互和任务正确性。
- [Agent Spec](https://github.com/oracle/agent-spec)：统一工作流设计参考。
- 自建 Runtime Microbenchmark：专门评测调度、资源管理、上下文、隔离和故障恢复；**不是 AgentRace 原生覆盖的所有能力**。

分两类对照：**统一功能对照**（固定共同工作流、模型、工具和外部执行环境，尽量隔离 Runtime 开销）；**原生能力对照**（允许各框架使用自己的编排与恢复能力，评价整体系统，但不把所有差异都归因于 Runtime）。

## 二、核心指标（P0）

### 1. 任务成功率

- Success Rate、Failure Rate；记录任务数和失败原因。
- Pass@1：单次尝试成功率，注明估计方法。
- Pass^k：同一任务重复 k 次均成功的可靠性；注意与 Pass@k 区分。
- 数据集：τ²-Bench 航空客服、Python 工程修复、多步骤工具调用。
- 不能丢弃失败记录、挑选最佳单轮或混用不一致的冻结版本。

### 2. 执行延迟

- 平均延迟、P50、P95、P99。
- Agent 启动、排队、调度、模型调用、工具执行时间。
- 单任务、多步骤任务、多 Agent 协作与固定模型响应回放。
- 并行情况下使用时间轨迹和关键路径分析，不应简单用总时间减各组件时间之和计算开销。

### 3. Token 与成本效率

- Input/Output/Total Tokens。
- Tokens per Successful Task、API Cost per Successful Task。
- 多轮工具调用、长上下文、多 Agent 共享文档。
- **框架内部上下文引用节省数据复制，不一定减少发送给模型 API 的 token**；分开统计。

### 4. 并发性能

- Throughput（任务/秒）、P50/P95/P99、Makespan、排队等待时间、最大稳定并发数、扩展效率。
- 并发建议：1/2/4/8/16/32；批次任务量：10/50/100/200。
- 分别进行 CPU 密集、I/O 密集、混合负载；标记超过硬件能力的配置。
- 同时报告吞吐量与尾延迟，避免无限排队造成虚假“高吞吐”。

### 5. 资源消耗

- CPU 使用率和 CPU Time；平均/峰值 RSS；进程数；cgroup 限流、OOM、进程数超限事件。
- 单 Agent、多 Agent、持续运行、受限环境。
- **包括 Runtime 管理器、Worker 和辅助进程自身开销**，记录采样频率和统计边界。

## 三、Runtime 专项指标（P1）

### 6. DAG 调度效率

任务图：完全串行、完全并行、多层依赖、节点耗时不均、资源竞争。

指标：DAG Makespan、调度决策耗时、Ready Queue 等待时间、Worker 空闲时间、CPU 利用率、相对关键路径下界的完成时间比值。

采用固定 DAG 与确定性工具负载，隔离 LLM 随机性。

### 7. 多 Agent 通信效率

场景：多个 Agent 读取相同资料并汇总；Agent 数 1/2/4/8/16。

指标：消息数量、内部传输字节数、序列化耗时、重复上下文传输量、共享引用访问延迟。区分内部 IPC 与模型请求 token。

### 8. 上下文管理效率

场景：多 Agent 重复读文档、长文本问答、多轮上下文积累、权限不同的资料读取。

指标：构造耗时、重复上下文比例、检索命中率、截断次数、输入 token、结果正确率和越权读取次数。

### 9. 故障恢复

故障：模型 API 超时、工具失败、Agent 进程退出、Runtime 重启、内存超限、短暂断网。

指标：Recovery Success Rate、Mean Recovery Time、状态丢失率、重复执行次数、有副作用操作重复次数、恢复后正确率。

注意：专项评测中断恢复不等于通用断点续跑；尚未实现的能力明确标为“不支持”。

### 10. 隔离与安全

测试：CPU/内存/进程超限、跨 Agent/用户未授权读、目录越界、非法工具参数。

指标：限制生效率、阻断率、正常请求误拒率、隔离开销、故障影响范围。

统一功能对照可用共享外部沙箱；原生能力对照则记录框架自身部署机制，不混同两者。

## 四、消融实验（P1）

| 组别 | 方案 | 验证目标 |
|---|---|---|
| A0 | 完整 Agent Runtime | 基线 |
| A1 | 关闭上下文共享优化 | 上下文机制收益 |
| A2 | 关闭资源感知准入策略，保留安全硬限制 | 资源调度收益 |
| A3 | 关闭非必要的多 Agent 协调 | 协调成本 |
| A4 | 关闭可选的详细追踪 | 观测开销 |
| A5 | 替换为简单 FIFO/固定调度 | 调度策略贡献 |

比较成功率、延迟、吞吐量、Peak RSS、token、通信量和调度开销；每组只改变一个变量。

## 五、控制变量和实验模式

固定/记录：
1. 模型供应商、模型 ID/版本、温度及采样参数。
2. 数据集版本、任务 ID、任务顺序和随机种子。
3. 提示词、工具协议、工具返回、最大步骤及预算。
4. 硬件、操作系统、Runtime 版本、commit SHA。
5. CPU/内存/进程/并发限制和外部沙箱。
6. 判分器、重试、超时和失败定义。
7. 热身次数、重复次数、统计方法和费用计算口径。

项目阶段材料的目标机器：16 GB NUC、openEuler 24.03 LTS-SP4（正式实验前复核）。

四种实验模式：
- **A 真实 LLM**：成功率、延迟、token、费用。
- **B 固定模型回复回放**：排除模型随机性，测 Runtime 固定开销。
- **C 确定性工具负载**：DAG、并发、资源隔离。
- **D 故障注入**：恢复能力、故障隔离和副作用幂等性。

不能将回放的模拟任务表现视为真实模型成功率。

## 八、与已有实验衔接

根据 2026-11-17 项目阶段材料，已有以下可复用基础（历史结果，**不是本评测方案的已实施结果**）：

- 固定回复的 50 条轨迹回放：直接调用 38.84 秒，自研 Runtime 66.27 秒，表明框架协调开销有待优化。
- 6 题小样本真实模型对照：成功数均为 6/6，直接调用 150.42 秒，Runtime 110.41 秒；样本过小，不足以得出普遍优势。
- τ²-Bench 航空客服：50 题 × 4 轮，共 200 次，成功 151 次，Pass¹ 为 75.50%；公开榜单状态仍需官方确认。
- Linux 资源约束、受控工具执行已有阶段性验证；通用故障恢复仍属于后续研发目标。

再次评测需固定模型、任务、工具、代码版本，不能混合不同冻结版本的成绩。

## 九、最终原则

我们不是只证明“Agent 能完成任务”，而是评价在**正确性不下降**的前提下，自研 Runtime 能否通过调度、资源管理和上下文机制带来更好性能、效率、扩展性与可靠性。必须保留失败和负面结果，不预设自研 Runtime 一定更优。
