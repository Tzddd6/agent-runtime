# 01. 多文件订单修复主场景、系统级多 Agent 视图与防假修复规格

## 一、多文件订单项目主场景（升级自单文件 `pricing`）

### 1.1 预置项目目录结构（可控、可复现）
在受控工程项目集（参考 `aios/tool/engineering.py`）中新增预置多文件项目 `order_service/`：
```text
order_service/
├── pricing.py        # 商品小计、阶梯折扣、优惠券边界
├── shipping.py       # 满额包邮、跨区附加费、重量计费
├── refunds.py        # 部分退款、运费退还规则、幂等校验（依赖 pricing & shipping）
└── tests/
    ├── test_public.py    # 公开测试（模型可见，用于初始失败复现与诊断）
    └── test_hidden.py    # 隐藏保留测试（严禁进入模型上下文，仅最终独立验收执行）
```
- **范围控制**：首版仅支持预置项目与受限白名单导入（限定文件列表、纯标准库依赖、固定 `unittest` 执行命令），不开放任意外部代码执行。
- **跨文件缺陷设计**：设计 2~3 处跨文件联动 Bug（例如 `pricing.py` 折扣后金额影响 `shipping.py` 免邮阈值，进而影响 `refunds.py` 退款上限），使单文件猜测无法通过全部测试。

### 1.2 端到端网页操作链路
用户在 Web Console（`http://127.0.0.1:8765/console/`）点击触发完整闭环：
1. **选择项目**（`order_service`）
2. **基线失败确认**：在独立工作区实际运行原始测试，记录明确失败日志与退出码
3. **分析 Agent（`analyst_agent`）**：读取源码与公开测试失败日志，产出结构化根因分析并写入 `ContextStore`，生成 `ctx_ref`
4. **修复 Agent（`patcher_agent`）**：通过 `ctx_ref` 读取上游分析，生成多文件补丁（支持修改 `pricing.py` / `shipping.py` / `refunds.py`）
5. **独立工作区应用补丁**：将补丁实际写入隔离工作区磁盘文件
6. **测试 Agent（`tester_agent`）**：在独立隔离 Worker 中运行公开测试 + 隐藏保留测试
7. **有界二轮修复（必要时）**：若首轮失败，携带失败日志动态派生 `patch_round_2 -> verify_round_2`（上限 1 轮，严格无环）
8. **评审与产物交付（`reviewer_agent`）**：汇总通过证明，生成**可下载压缩包**（含统一 diff 补丁、完整测试日志、修改后的完整项目源码及 `SHA256SUMS.txt`）

## 二、让“多 Agent”在系统层面成立

### 2.1 内核级实体隔离
- `analyst_agent`、`patcher_agent`、`tester_agent`、`reviewer_agent`（以及可选的独立无依赖辅助分支，如 `audit_agent` 做静态合规/依赖检查）必须拥有：
  - 独立的 **Agent ID** 与 **ACB（Agent Control Block）**；
  - 独立的 **资源配额与模型/Token 预算账本**；
  - 仅对**确实无数据依赖的节点**做并行调度（如分析阶段并行跑“失败日志诊断”与“静态规则审计”），有依赖节点严格按 DAG 拓扑推进。

### 2.2 控制台实时可观测性（评委必看项）
后端快照 API（`runtime/web.py`）与前端面板（`runtime/static/native-console.js`）必须实时呈现并与后端状态强一致：
1. **DAG 节点状态**：`pending / running / waiting / done / failed / skipped`，动态派生出 `patch_round_2` / `verify_round_2` 时图谱实时更新；
2. **OS 资源映射**：每个 Agent 对应哪个 **Worker、真实 PID、`cgroup` 路径**（Linux 实机显示真实委派子组路径，Windows 显示受控隔离模式说明）；
3. **精细账本**：每个 Agent 消耗的 **CPU/内存、模型调用次数、输入/输出 Token 数**；
4. **数据流血缘**：明确展示上游结果如何通过 **`ctx_ref`（SHA-256 引用 ID）** 传递给下游，而非全量重复拷贝；
5. **非级联容错演示**：提供一个可控故障分支（如无依赖审计 Agent 故意失败或预算耗尽），控制台清晰显示该分支标红失败且有明确原因，同时主修复链路照常完成并交付。

## 三、6 条“防假修复成功”硬门槛（必须有自动化单测锁定）

| # | 硬门槛要求 | 工程实现与验收方式 |
|---|---|---|
| 1 | **参考答案与隐藏测试不进入模型上下文** | 构造给模型的 Prompt/上下文时严格过滤 `tests/test_hidden.py` 及任何参考答案文件；单元测试拦截并断言模型请求载荷中不含隐藏测试内容。 |
| 2 | **测试文件不可被修复 Agent 修改或删除** | 应用补丁前校验补丁目标路径白名单（禁止触碰 `tests/`），并在运行测试前后比对 `tests/` 目录所有文件 SHA-256，任何改动直接判失败。 |
| 3 | **零测试、全跳过、超时一律不算成功** | 解析 `unittest` 实际执行结果：要求 `tests_run > 0`、`skipped < tests_run`、`failures == 0`、`errors == 0`、`timed_out == False`，缺一不可。 |
| 4 | **补丁必须落盘到实际文件再跑测试** | 禁止仅在内存中 `exec` 拼接字符串；必须在独立工作区写入真实 `.py` 文件后再启动隔离测试子进程。 |
| 5 | **下载产物源码摘要与通过测试的源码强一致** | 测试通过后立刻计算工作区源码树 SHA-256 并写入交付清单；下载 zip 后校验包内源码哈希与已通过测试的工作区哈希完全一致。 |
| 6 | **中断后不盲目重放写操作或付费调用** | 复用并验证幂等键/状态机保护：刷新页面、重复点击或进程重启后不重复触发写文件或付费模型请求。 |
