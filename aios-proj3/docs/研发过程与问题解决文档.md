## 二、真实踩坑与排障实录（工程难点闭环）

### 坑 1：纯内存持钥进程 `ModelService` 单 Pipe 锁导致真并发串行化
- **现象**：内核调度层已实现零空等并发派发，但 NUC 实测 4 并发真实 DeepSeek API 竟耗时 `4.916s`（比裸 4 并发 `1.322s` 慢 3.7 倍）。
- **根因**：`ModelService` 为隔离密钥使用单一 `Pipe` 加 `self.lock`，导致所有并发请求在跨进程管道边界退化为串行。
- **解决**：重构 [aios/llm_core/model_service.py](../aios/llm_core/model_service.py) 为**请求 ID 多路复用协议 + 持钥子进程内 `ThreadPoolExecutor(16)` + 父进程异步解复用线程**；在保持业务子进程零 API Key 继承的前提下，4 并发实测降至 **`0.542s`（9.07× 提速）**，8 并发 `8/8` 仅 **`1.115s`**。

### 坑 2：openEuler 非 root 委派 `cgroup v2` 与 `systemd-run` 变量提前展开
- **现象**：在 `FINAL_CHECK.sh` 中用 `systemd-run --user -p Delegate=yes /bin/bash -c '...'` 初始化委派子组时，先遇到 `mkdir: 无法创建目录 "/aios_self"`，修复后又触发 `ProcessService` 报错 `Delegated Worker subtree contains unreconciled groups`。
- **根因**：① `systemd-run` 会将 `ExecStart` 中的 `${CG_ROOT}` 在启动 bash 前预先展开为空；② `cgroup v2` 要求内部进程必须迁入子组才能开启 `cgroup.subtree_control`，但若将 `aios_self` 与 Worker 放在同一层目录，`ProcessService` 的零孤儿守卫会将其误判为遗留子组。
- **解决**：将初始化逻辑写入隔离辅助脚本 `_run_delegated.sh`，并建立平级双子组 `${CG_ROOT}/aios_self`（承载当前进程）与 `${CG_ROOT}/workers`（干净子树传给 `AIOS_TEST_CGROUP_ROOT`），实现 89/99 全量测试与 `validate_linux.py` 100% 绿灯。

### 坑 3：Bare 对照组挖出 `adapter.py` 截断守卫误触 `502`
- **现象**：`AgentBench OS` 初次运行 AIOS 仅 `10/26`（4 题首轮报 `llm_error_502`），而 Bare 直接 HTTPS 达到 `16/26` 且零 `502`。
- **根因**：[aios/llm_core/adapter.py](../aios/llm_core/adapter.py) 实现了刻意设计的 **fail-closed 截断守卫**（遇到 `finish_reason="length"` 主动返回 `502` 拒绝执行半截 Shell 命令或残缺 JSON 工具调用），而原评测脚本 `max_new_tokens=512` 偏紧，导致长思维链触发截断。
- **解决**：保留 `adapter.py` 安全契约不动，将多轮评测脚本预算调至 `1536` 并引入线程安全 4 路并发后，全部真实云端任务实现 **零 `502` 误杀**，`AgentBench OS` 通过率立刻回升至 **`16/26`（追平 Bare）** 且耗时降至 **`67.29s`（比 Bare 快 1.88×）**。

### 坑 4：两轮独立边界测试暴露的 12 项系统缺陷 + 5 项交付复核缺陷（`OA-01`~`OA-05`）
- **多作用域与 IPC 生命周期缺陷**：引入 `TaskScope` `_active_scopes` 互斥锁与 `ContextStore` `_holders` 引用计数租约，解决共享上下文误删与发送方退出导致接收方引用失效；`delete()` 改为 SQLite 先提交、磁盘删除失败即回滚的两阶段原子操作；日志处理器改为 `_SafeStreamHandler` 屏蔽 `BrokenPipeError`。
- **交付与控制台边界缺陷（`OA-01`~`OA-05`）**：
  - 移除未配置模型时的隐式参考答案降级（必须显式启用 `deterministic_stub`）；
  - 修正 `runtime/web.py` 中 `cgroup_manager.root_path → cgroup_root` 属性错名；
  - `download_zip()` 下载时强制二次核验 ZIP SHA-256 与源码树摘要，且交付包附带 `tests/test_public.py`；
  - `ChatStore.intent()` 幂等签名补齐 `project` 与 `model_budget`，冲突时拒绝且不覆盖旧成功记录；
  - 控制台遥测改为按任务计算 ACB 增量差值，且对无独立 Worker 的角色如实显示 `N/A (no isolated OS worker)`，杜绝伪造路径。

## 三、与类似项目及前沿研究的系统对比

### 3.1 与主流框架及原版 AIOS 对比

| 对比维度 | LangChain / AutoGen / CrewAI（应用层框架） | 原版 `agiresearch/AIOS`（学术原型） | Bare 直接 HTTPS 循环 | **本系统 AIOS-Proj3（openEuler OS 级运行时）** |
|---|---|---|---|---|
| **OS 级硬隔离（`cgroup v2`）** | 无（单进程线程/协程） | 无原生 `cgroup v2` 委派控制器 | 无 | **openEuler 委派 `cgroup v2`（CPU `0.20` 核限流 + OOM 隔离 + 零孤儿）** |
| **常驻进程监督与崩溃自愈** | 无 | 无 `AF_UNIX` 崩溃监督器 | 无 | **Linux `AF_UNIX` 常驻 Worker 心跳 + `SIGKILL` 自动拉起（不重放写操作）** |
| **凭据安全与真并发兼顾** | 环境变量透传，子进程可读 Key | 单进程共享凭据 | 环境变量直连 | **独立 `spawn` 纯内存持钥进程 + 请求 ID 多路复用（4 并发 `0.542s`）** |
| **上下文复用与 IPC 隔离** | 内存对象/重复序列化 | 基础上下文管理 | 无 | **SHA-256 去重 + `_holders` 引用计数 + `Mailbox` ACL 撤销 + 零拷贝 `ctx_ref`** |
| **防“假修复成功”工程闭环** | 依赖手工脚本 | 无 | 依赖手工脚本 | **隐藏测试隔离 + 只读测试校验 + 落盘实测 + 下载 ZIP SHA-256 二次验签** |
| **单次串行短调用开销** | 中~高 | 低~中 | **最低（无转发层）** | 存在少量内核调度/隔离开销（固定桩受控对照已如实量化） |

### 3.2 与 2026 年最新系统研究《AgentCgroup》的呼应
2026 年 2 月最新研究 **《AgentCgroup: Understanding and Controlling OS Resources of AI Agents》**（Zheng et al., [arXiv:2602.09345](https://arxiv.org/abs/2602.09345)，`eunomia-bpf/agentcgroup`）对主流编程智能体进行了系统级画像，实测发现 **OS 与工具执行层占据 55%–74% 的端到端耗时**，且工具调用会引发高达 **15.4× 的内存尖峰**，因此提出必须以**“工具调用粒度”构建分层 `cgroup v2` 资源边界**。本系统 `ProcessService` 按工具子任务粒度动态创建委派 `cgroup v2` 子组、施压限流并在退出时强制回收零孤儿目录的设计，与该最新前沿研究的核心发现高度一致。
